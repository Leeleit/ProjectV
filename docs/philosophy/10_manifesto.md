# Манифест: производительность как обязательство

Документ описывает фундаментальные принципы разработки высокопроизводительного
real-time движка.

---

## Принцип 1: производительность — обязательство, а не опция

В real-time приложениях (60 FPS игры, симуляции, финансовые системы с
microsecond latency) бюджет времени на кадр фиксирован. Для 60 FPS это 16.6
мс. Для 120 FPS — 8.3 мс. Превышение бюджета = бракованный кадр.
Бракованный кадр = бракованный движок.

Один кадр обрабатывает миллионы вокселей, миллионы лучей, миллионы
операций. Это возможно только если архитектура спроектирована под нагрузку
с первого дня.

## Принцип 2: данные важнее кода

Структуры данных определяют архитектуру. Не классы, не методы, не
паттерны — структуры данных.

Две точки зрения:

- ООП-мышление: «Какие методы у объекта?»
- DOD-мышление: «Как массив данных обработать линейным проходом?»

Код — инструмент трансформации данных. Плохая структура данных убивает
любой алгоритм.

## Принцип 3: память — узкое место

Процессор выполняет ~100 инструкций, пока данные идут из RAM.

| Уровень | Латентность |
|:--------|:------------|
| L1 кэш | 4-5 тактов |
| L2 кэш | 12-15 тактов |
| L3 кэш (если есть) | 40-50 тактов |
| RAM (DDR5) | 200-300 тактов |

Числа — порядок величин для x86 P-core 2025-2026. Apple Silicon отличается:
128-байтные кэш-линии, отсутствие L3 в пользу единого L2 до 16 MB на
кластер, unified memory.

Пока процессор ждёт данные — он простаивает. Задача: упаковать данные
так, чтобы нужное лежало ближе.

## Принцип 4: оптимизация — не финальный этап

Медленный код — архитектурная ошибка, а не свойство железа. Если код
работает медленно, задача не понята до конца. Никакие микрооптимизации
не маскируют плохую архитектуру.

---

## Правила разработки

### Не оптимизируй преждевременно

Линейный поиск по массиву часто быстрее хеш-таблицы на малых N.
Предсказатель ветвлений и кэш процессора любят простые циклы.

### Читаемость важнее краткости

Код читается чаще, чем пишется. Умный код непонятен через месяц.

### Low latency важнее throughput

Real-time приложения требуют не пропускной способности, а
предсказуемости. Стабильные 16.6 ms лучше, чем в среднем 12 ms со
спайками до 50. Оптимизируй для p99 latency, не для среднего.

### Знай цену каждой абстракции

Каждый `virtual` — косвенный вызов. Каждый `new` — поиск в куче. Каждый
cache miss — 100+ потерянных тактов. Абстракции полезны, но цена каждой
должна быть известна.

## Подход к разработке

### Гипотеза → измерение → решение

Каждое архитектурное решение — ставка: «Если я расположу данные так,
будет быстрее». Ставки проверяются профилировщиком (Tracy 0.13.1,
VTune, uProf). Гипотеза не подтвердилась — откатываем.

### Техническая честность

C++ даёт доступ к железу. Цена каждой абстракции известна и осознанна:

| Конструкция | Стоимость | Когда использовать |
|:------------|:----------|:-------------------|
| `virtual` | Косвенный вызов + возможный cache miss | Интерфейсы с одним объектом |
| `std::shared_ptr` | Атомарные операции + control block | Разделяемое владение (редко) |
| `new` | Аллокация в куче | Только для долгоживущих объектов |
| `std::vector::push_back` | Возможная реаллокация | После `reserve()` |
| `std::map` | Дерево + косвенность | Когда нужна упорядоченность |
| `std::unordered_map` | Хеш + возможные коллизии | Только для редких lookups |

Контекст определяет выбор. Hot path и UI требуют разных подходов.

### Архитектура без магии

Читая код, разработчик должен понимать не только **что** он делает, но и
**почему** написан именно так. Никакой магии — всё должно быть объяснимо.

Пример: в ECS нет базового класса `Entity`. `Entity` — это `uint64_t`
(идентификатор). Нет данных — нет проблем с наследованием. Композиция
через компоненты — следствие понимания данных, не паттерн ради паттерна.

## Пример: применение в движке

Принципы реализованы в ProjectV (песочница в духе War Thunder, Foxhole,
HoI4). Например, ECS через flecs v4.1 даёт SoA layout через archetypes;
mesh shaders рендерят чанки вокселей напрямую с GPU; timeline semaphores
координируют CPU↔GPU очереди.
