# Оптимизация

Документ описывает иерархию оптимизации в высокопроизводительных
системах.

---

## Бюджет кадра

В real-time приложениях (60 FPS игры, симуляции, финансовые системы с
microsecond latency) бюджет времени на кадр фиксирован. Для 60 FPS это
16.6 мс. Для 120 FPS — 8.3 мс. Превышение бюджета = бракованный кадр.
Бракованный кадр = бракованный движок.

Медленный код — архитектурная ошибка, а не свойство железа. Если код
работает медленно, задача не понята до конца.

## Иерархия оптимизации

Оптимизация применяется на трёх уровнях. Каждый следующий даёт меньше
выигрыша.

### Уровень 1: данные (×10-100)

Самый важный уровень. Плохо организованные данные убивают любой
алгоритм.

- **Cache locality:** данные, обрабатываемые вместе, лежат рядом.
- **Memory bandwidth:** минимизация чтений из RAM.
- **Hot/cold splitting:** разделение часто и редко используемых полей.
- **Data layout:** правильное выравнивание и упаковка структур.

Правильная организация данных даёт ускорение в 10-100×. Это
фундамент.

### Уровень 2: алгоритм (×2-10)

Выбор структуры данных и сложности алгоритма.

- **O(N) vs O(N²):** линейный поиск по массиву часто быстрее
  `std::map` на малых N.
- **Batch processing:** обработка пачками, а не по одному элементу.
- **Cache-oblivious algorithms:** алгоритмы, оптимальные независимо
  от размера кэша.

O(N) может быть быстрее O(log N). Big-O игнорирует константы.

### Уровень 3: код (×1.1-1.5)

Микрооптимизации — последний шаг.

- **SIMD/AVX:** векторизация горячих циклов.
- **Branchless:** убрать `if` из критических путей.
- **Inlining:** помочь компилятору встраивать маленькие функции.

Микрооптимизации работают только после оптимизации данных и
алгоритма.

---

## Правило: оптимизация снизу вверх

Если начинаешь с уровня 3 — оптимизируешь не то.

Пример:

1. Уровень 1: переход с AoS на SoA. 10× ускорение.
2. Уровень 2: замена hash map на flat array. 2× дополнительно.
3. Уровень 3: SIMD-векторизация batch processing. 1.3× дополнительно.

Итого: 26× ускорение.

Если начать с уровня 3 без уровня 1: 1.5× ускорение.

## Память — узкое место

Процессор выполняет ~100 инструкций, пока данные идут из RAM.
Подробности в [05_hardware-tour.md](05_hardware-tour.md).

| Уровень | Латентность |
|:--------|:------------|
| L1 кэш | 4-5 тактов |
| L2 кэш | 12-15 тактов |
| L3 кэш (если есть) | 40-50 тактов |
| RAM (DDR5) | 200-300 тактов |

Пока процессор ждёт данные — он простаивает. Задача: упаковать данные
так, чтобы нужное лежало ближе.

## Branch prediction

Современный CPU «угадывает», какая ветка `if` сработает. Угадал —
конвейер летит. Ошибся — сброс (10-20 тактов штрафа).

Способы минимизации mispredict:

- **Branchless код:** заменить `if (x) a = b; else a = c;` на
  `a = cond ? b : c;` или без условных переходов.
- **Сортировка данных:** данные, где условие срабатывает одинаково,
  группируются.
- **`[[likely]]` / `[[unlikely]]`:** подсказки компилятору.

Если данные отсортированы так, что `if` всегда срабатывает одинаково,
процессор угадывает почти всегда.

## Компромиссы

В реальных проектах бывают обоснованные компромиссы:

- **Читаемость:** иногда чуть более медленный, но понятный код лучше.
- **Скорость разработки:** `std::string` в UI — нормально.
- **Безопасность:** `std::span` и `assert` вместо сырых указателей — правильный
  выбор.

В hot path (рендеринг, физика, мешинг) — никаких компромиссов.
Hot path — это код, который выполняется каждый кадр, обрабатывает
миллионы элементов.

Cold path (UI, загрузка уровней, сохранение) — пишется читаемо.

---

## Золотое правило

**Измеряй, не гадай.**

Интуиция врёт систематически. Профайлер не врёт. Не оптимизируй то,
что не измерено. Не меряй то, что не в критическом пути. Оптимизируй
то, что профайлер показывает как узкое место.

## Пример: применение в движке

В ProjectV иерархия оптимизации применяется систематически: сначала
проверка layout данных (SoA через flecs archetypes), затем выбор
алгоритма (batch processing в meshlet generation), затем SIMD через
`std::simd` в voxel processing. Профилировщик — Tracy 0.13.1 в Debug и
Release.
