# Об этом гайде

Документ описывает сам гайд, не движок. Зачем существует, как устроен,
для кого.

---

## Что это

`docs/philosophy/` — карта принципов разработки высокопроизводительных
real-time движков. Гайд объясняет **что** и **почему**, и указывает,
**где** читать подробности. Это не «как писать код» — для этого есть
конкретные проекты с их `src/`.

---

## Для кого

- **Новый разработчик в проекте.** Хочет понять, почему здесь всё
  устроено именно так. Начать с [02_how-to-read.md](02_how-to-read.md) →
  маршрут «1 день».
- **Контрибьютор извне.** Хочет предложить PR, но не уверен, что стиль
  совпадает. Прочитать [10_manifesto.md](10_manifesto.md),
  [11_anti-patterns.md](11_anti-patterns.md) и
  [90_code-review-checklist.md](90_code-review-checklist.md).
- **Автор проекта через полгода.** Забыл, почему было принято решение.
  Заглянуть в [01_glossary.md](01_glossary.md).
- **Студент / любопытный.** Хочет понять, как устроены современные
  движки. Начать с [04_what-is-a-game-engine.md](04_what-is-a-game-engine.md).

---

## Чего тут нет

### Нет длинных примеров кода

Код живёт в `src/` конкретных проектов, меняется каждый день,
устаревает мгновенно. В гайде оставлено ровно столько кода, сколько
нужно для иллюстрации одного конкретного принципа (1-3 строки). Длинные
примеры заменены на указатели «см. в `src/<path>`».

### Нет пошаговых туториалов

Этот гайд не научит писать движок. Для этого есть:

- Jason Gregory, *Game Engine Architecture*, 4ed (2026) — канонический
  двухтомник.
- Mike Acton, *Data-Oriented Design and C++*, CppCon 2014 — канонический
  доклад по DOD.
- Vittorio Romeo, *More Speed & Simplicity: Practical DOD in C++*,
  CppCon 2025 keynote — свежее переосмысление DOD.
- Herb Sutter, *C++26 is done!*, trip report March 2026 — статус C++26.

Полный список — [92_external-sources.md](92_external-sources.md).

### Нет схем

Диаграммы иллюстрируют поток данных или последовательность вызовов.
Это «как», а не «что». Если нужна схема — открыть `src/` конкретного
проекта и прочитать имена функций в порядке вызова.

## Как устроена нумерация

Файлы лежат **плоско** в `docs/philosophy/`. Имя файла — `NN_short-name.md`,
где `NN` — порядковый номер для чтения:

| Диапазон | Раздел | Назначение |
|:---------|:-------|:-----------|
| `00-09` | Frontmatter | readme, глоссарий, маршруты чтения, введение для неэксперта |
| `10-19` | Фундамент | принципы, анти-паттерны, решения, хаки, компилятор, compile-time, память, ошибки, layout, отладка |
| `20-29` | Парадигмы | zero-cost, DOD, ECS, конкурентность, поток данных, строки |
| `30-39` | Домен | оптимизация, Vulkan, воксели, тестирование, математика, время |
| `90-99` | Практика | code review, tooling, источники, перформанс-методология, build & CI |

Свободные диапазоны оставлены для будущих вставок.

---

## Конвенции

- **Markdown only.** Никаких бинарных вложений.
- **Одна тема = один файл.**
- **Секция «Источники и дальнейшее чтение» в конце каждого файла.**
- **Кросс-ссылки через относительные пути** (`[X](10_manifesto.md)`).

---

## Как НЕ надо пользоваться этим гайдом

- **Не цитировать как спецификацию.** Это принципы, не контракт.
- **Не использовать как чек-лист «прочитал → могу писать код».**
- **Не апдейтить содержимое «потому что ИИ сгенерировал».**
