# Методология измерений

Документ описывает, как правильно измерять производительность
высокопроизводительных систем.

---

## Почему «5-10%» — порог значимости

В экспериментах с движками (benchmarks, A/B-сравнения алгоритмов)
используется порог **5-10%** для определения значимой разницы.

Меньше 5%:

- Шум измерения.
- Зависимость от окружения (temperature, throttling, другие процессы).
- Random variance в системе.

5-10%:

- Возможная значимая разница.
- Требует повторных замеров для подтверждения.
- Решение принимается после 3+ запусков с медианой.

Больше 10%:

- Значимая разница.
- Решение принимается сразу.
- Требуется обоснование в engineering contract.

Порог 5-10% — эвристика, а не абсолют. Для GPU-bound операций
(рендеринг) — строже (10%+). Для CPU-bound (физика, ECS) —
мягче (5%+).

## Иерархия измерений

Измерения проводятся на четырёх уровнях. Каждый следующий даёт больше
информации и стоит больше времени.

### Уровень 1: microbenchmark

Google Benchmark на изолированной функции или алгоритме.

```cpp
static void BM_GreedyMeshing(benchmark::State& state) {
    auto chunk = generate_standard_chunk();
    for (auto _ : state) {
        auto mesh = greedy_mesh(chunk);
        benchmark::DoNotOptimize(mesh);
    }
}
BENCHMARK(BM_GreedyMeshing);
```

Цель: сравнить два алгоритма на одних данных. Решение: какой быстрее
на 5-10%+.

### Уровень 2: frame benchmark

Замер кадра в реальной сцене.

```cpp
auto start = std::chrono::high_resolution_clock::now();
world.progress(dt);
render_frame();
auto end = std::chrono::high_resolution_clock::now();
auto frame_time = std::chrono::duration_cast<ns>(end - start).count();
```

Цель: среднее, p99, max frame time. Решение: оптимизировать систему,
показывающую > 1 ms в Tracy.

### Уровень 3: workload benchmark

Замер в реалистичной сцене (1000 вокселей, 100 сущностей, lighting).

Цель: воспроизводимая производительность в типичных условиях.

### Уровень 4: production profile

Профилирование в production-like условиях (release build, реальные
ассеты, реальные сценарии).

Цель: финальная валидация перед релизом.

## Гипотеза → измерение → решение

Каждое решение о производительности проходит три шага.

### Шаг 1: гипотеза сформулирована

Не «ускорить эту функцию». А: «Если заменить hash map на flat array,
frame time уменьшится на X% потому что Y».

Гипотеза включает:

- Что меняется.
- Почему должно быть быстрее.
- Ожидаемый эффект (в процентах или абсолютных числах).

### Шаг 2: измерение baseline

Перед изменением — измерение baseline. Без baseline невозможно оценить
эффект.

```cpp
// Baseline
auto baseline_frame_time = measure_frame_time(workload);
// 16.4 ms
```

### Шаг 3: изменение

Изменение реализуется. Перед коммитом — повторное измерение.

```cpp
// After change
auto new_frame_time = measure_frame_time(workload);
// 14.2 ms
// Δ = -13.4%
```

### Шаг 4: решение

Если Δ > 5-10% — изменение принимается. Если Δ < 5% — изменение
отклоняется (или остаётся для читаемости, если автор настаивает).

## Когда оптимизация окупается

Оптимизация окупается когда:

- Измеренный bottleneck > 1 ms в реальном кадре.
- Измеренная экономия > 5-10% от текущего значения.
- Изменение не ломает читаемость и тестируемость.

Оптимизация НЕ окупается когда:

- Bottleneck не показан профилировщиком.
- Экономия < 5% и не критична.
- Изменение усложняет код без явной выгоды.

## Рабочий процесс с Tracy

Tracy — основной профилировщик. Workflow:

### Шаг 1: instrument hot path

```cpp
FrameMark;  // начало кадра
ZoneScoped; // зона текущей функции
ZoneScopedN("PhysicsSystem::update"); // именованная зона
```

### Шаг 2: capture

Запуск с Tracy UI (TCP подключение). Сохранение capture.

### Шаг 3: анализ

- Flame graph: какая система съела больше всего.
- Memory: где аллокации.
- Locks: contention.
- GPU vs CPU: где bottleneck.

### Шаг 4: optimize

Изменение кода на основе измерения. Повторное измерение для проверки.

### Шаг 5: regression check

Если изменение замедляет какую-то другую систему — откат или
компенсация.

---

## Когда оптимизация НЕ окупается

Cold path — UI, загрузка уровней, сохранение игры. Оптимизация cold
path за счёт читаемости — антипаттерн.

```cpp
// Cold path: нормальный код
auto config = read_config("settings.json");

// Hot path: оптимизированный код
process_chunk_simd_avx512(chunk_data, count);
```

Оптимизация cold path не оправдана: пользователь не заметит разницы,
а код станет менее читаемым.

## Методология принятия решений

Решение об оптимизации принимается по результатам измерения:

1. Профилировщик показывает bottleneck.
2. Bottleneck занимает > 1 ms в реальном кадре.
3. Гипотеза об оптимизации сформулирована.
4. Baseline измерен.
5. Изменение реализовано.
6. Новое измерение показывает улучшение > 5-10%.
7. Изменение задокументировано в engineering contract.
8. PR создан.

Без всех 8 шагов — изменение не принимается.
