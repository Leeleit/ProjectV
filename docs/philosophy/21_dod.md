# Data-Oriented Design

Документ описывает Data-Oriented Design (DOD) — подход к проектированию
через данные, а не через объекты.

---

## 12 принципов Майка Актона

Майк Актон (Engine Director, Insomniac Games) сформулировал 12
принципов DOD в CppCon 2014 keynote. Переформулировка Лучиана Раду
Теодореску (ACCU Overload 30/167, декабрь 2022) и Витторио Ромео
(CppCon 2025 keynote) расширяет их для 2020-х.

### Принципы (DOD-P1 ... DOD-P12)

**DOD-P1.** Цель любой программы и любой её части — трансформация
данных из одной формы в другую.

**DOD-P2.** Если ты не понимаешь данные, ты не понимаешь задачу.

**DOD-P3.** Понимай задачу через понимание данных (обратное к P2).

**DOD-P4.** Разные задачи требуют разных решений.

**DOD-P5.** Разные данные — разная задача.

**DOD-P6.** Если ты не понимаешь стоимость решения, ты не понимаешь
задачу.

**DOD-P7.** Если ты не понимаешь железо, ты не можешь рассуждать о
стоимости решения.

**DOD-P8.** Всё — задача про данные. Включая usability, maintainability,
debug-ability.

**DOD-P9.** Решение проблем, которых у тебя нет, создаёт проблемы,
которые у тебя будут.

**DOD-P10.** Latency и throughput — одно и то же только в
последовательных системах. В параллельных — разное.

**DOD-P11.** Софт не работает в волшебной среде, придуманной CS PhD.

**DOD-P12.** Один есть много. Ищи на оси времени.

### Правила большого пальца

- **DOD-ROT1.** Где один, там много. Ищи на оси времени (агрегация
  исторических данных, батчинг операций).
- **DOD-ROT2.** Чем больше контекста, тем лучше решение. Не выбрасывай
  данные, которые нужны.
- **DOD-ROT3.** NUMA расширяется до I/O и предсобранных данных назад во
  времени до момента создания исходных данных.

## Смена парадигмы: от объектов к данным

### ООП-мышление

«Какой объект мне нужен? Какие методы у него должны быть?»

Методы проектируются от интерфейса. Данные — реализация интерфейса.

### DOD-мышление

«Какой массив данных мне нужен? Как я его обработаю линейным проходом?»

Данные проектируются от layout'а. Код — трансформация данных.

## SoA (Structure of Arrays) vs AoS (Array of Structures)

### AoS

```cpp
struct Particle {
    vec3 position;
    vec3 velocity;
    float mass;
};
std::vector<Particle> particles;
```

При обработке позиций в кэш попадают velocity и mass. На 64 байтную
кэш-линию — 8 частиц. Из них 4 байта position, остальное — мусор.

### SoA

```cpp
struct Particles {
    std::vector<vec3> positions;
    std::vector<vec3> velocities;
    std::vector<float> masses;
};
```

При обработке позиций в кэш попадают только позиции. На 64 байтную
кэш-линию — 8 vec3 = 96 байт данных.

### Когда что

- **SoA:** большие структуры (> 32 байт), hot loop обрабатывает часть
  полей, миллионы объектов.
- **AoS:** маленькие структуры (< 16 байт), объекты обрабатываются
  целиком, редкие операции.

См. [18_data-layout.md](18_data-layout.md).

## Hot/Cold splitting

Данные делятся на:

- **Hot:** используются каждый кадр. Position, velocity, transform.
- **Cold:** используются редко. Name, owner, metadata.

Размещение раздельно:

- Hot data обрабатывается в hot loop, кэш не загрязняется cold полями.
- Cold data загружается по необходимости.

См. [18_data-layout.md](18_data-layout.md).

## Пакетная обработка

Обработка пачками, а не по одному элементу:

- Параметры функций один раз на пачку.
- Указатели инкрементируются линейно.
- Cache miss-ы минимальны.
- SIMD-векторизация возможна.

```cpp
for (size_t i = 0; i < n; i += 8) {
    vec8 pos = load_vec8(&positions[i]);
    vec8 vel = load_vec8(&velocities[i]);
    vec8 new_pos = pos + vel * dt;
    store_vec8(&positions[i], new_pos);
}
```

SIMD обрабатывает 8 элементов за раз.

## Принципы DOD в разработке

1. **Данные важнее кода.** Архитектура определяется layout'ом данных.
2. **POD-структуры.** Hot path компоненты — POD с тривиальными
   конструкторами и деструкторами.
3. **SoA через archetype-based системы.** Компоненты одного типа
   хранятся в массивах автоматически.
4. **Hot/cold splitting.** Разделение критичных и некритичных данных.
5. **Batch processing.** Обработка пачками одним проходом.
6. **Измерение важнее интуиции.** DOD-решения принимаются после
   профилирования.

## Как думать данными: практика

### Шаг 1: определить данные

Не методы, не классы. Данные. Что есть в мире, как они связаны.

### Шаг 2: определить трансформации

Какие операции над данными? Какие из них выполняются каждый кадр?

### Шаг 3: разделить hot и cold

Hot операции определяют layout данных.

### Шаг 4: реализовать

Код — линейные проходы по массивам. Без виртуальных вызовов. Без
pointer chasing.

### Шаг 5: измерить

Профилировщик показывает, что быстрее: SoA или AoS, hot/cold split
или нет, batch processing или per-element.

## Пример: применение в движке

В ProjectV DOD применён повсеместно: компоненты ECS — POD, archetypes
flecs автоматически дают SoA layout, hot/cold splitting в entity
структурах, batch processing в meshlet generation через compute
shaders.
