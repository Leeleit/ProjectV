# Злые хаки

Документ описывает, когда нарушение правил оправдано.

---

## Что такое злой хак

Злой хак (evil hack) — техника, которая:

- Нарушает одно из правил [11_anti-patterns.md](11_anti-patterns.md).
- Решает конкретную измеримую проблему.
- Локализована (не распространяется на остальной код).
- Документирована как злой хак.

Без этих четырёх пунктов — не злой хак, а просто плохой код.

---

## Когда злой хак оправдан

### Измеренная проблема

Профилировщик показывает 6 ms в одной функции. Профилировщик однозначно
указывает на bottleneck. Без измерения — не злой хак, а догадка.

### Решение не найдено в рамках правил

Перепробованы: оптимизация алгоритма, реорганизация данных, изменение
порядка операций. Правильные подходы не дают нужного выигрыша.

### Локализация

Хак живёт в одной функции, одном файле, одной подсистеме. Не
распространяется на архитектуру. Не становится «паттерном» для
подражания.

### Документация

Комментарий в коде объясняет: что делает хак, какую проблему решает,
какие альтернативы отвергнуты и почему. Ссылка на профиль или benchmark,
который обосновывает выбор.

---

## Когда злой хак не оправдан

### «Это быстрее» без измерения

Сомнительная экономия в 5% не стоит нарушения правил. Правила
нарушаются только когда измерение показывает, что без хака невозможно.

### Хак как shortcut для лени

«Не хочется переписывать алгоритм» — не причина для хака.

### Хак без документации

Недокументированный хак превращается в технический долг.

---

## Категории злых хаков

### Unsafe memory operations

`std::memcpy` вместо копирования по элементам. `reinterpret_cast` для
сериализации POD. Чтение/запись через union.

Оправдано: ABI-совместимость, горячий путь сериализации, интринсики SIMD.
Не оправдано: лень переписывать.

### Hard-coded offsets

Фиксированные смещения в структурах вместо полей. Прямой доступ к
байтам через `(uint8_t*)&struct`.

Оправдано: совместимость с бинарным форматом, заголовки пакетов сети.

### Inline ассемблер или платформенные intrinsic'и

`__builtin_expect`, `__builtin_prefetch`, `_mm_*` intrinsics.

Оправдано: hot path с измеренным эффектом.

### Удаление проверок в debug-сборке

Проверка замедляет hot path, инвариант гарантирован выше по стеку.

Оправдано при подтверждённом overhead. Не оправдано по лени.

### Глобальные переменные для hot data

`static ThreadLocal MyData` вместо передачи через аргументы.

Оправдано: данные hot path, передача через аргументы создаёт overhead.

## Правила использования

1. Каждый хак начинается с измерения.
2. Каждый хак документируется в коде. Комментарий «это злой хак»
   обязателен.
3. Каждый хак локализован. Файл, функция, подсистема. Не паттерн.
4. Каждый хак пересматривается. Раз в год — стоит ли ещё этот хак
   проблемы.
5. Хаки не пишутся в новом коде. Сначала правильное решение. Если
   правильное не решает — хак.

---

## Когда удалить хак

Удалить хак можно, когда выполнено одно из условий:

- Измерение показывает, что хак больше не нужен (новый компилятор, новая
  фича языка, изменение условий).
- Замена найдена в рамках правил и проверена измерением.
- Архитектурное изменение устраняет причину хака.

Удаление хака — отдельный коммит с обоснованием.

## Пример: применение в движке

В ProjectV (и в других крупных движках типа Unreal Engine, Naughty Dog
движков) злые хаки — стандартная практика в hot path рендеринга и
физики. Каждый хак помечен комментарием `EVIL` и ссылкой на
профилирование, его обосновывающее.
