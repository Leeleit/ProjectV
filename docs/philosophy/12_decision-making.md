# Принятие технических решений

Документ описывает критерии и процесс выбора между вариантами в
инженерных проектах.

---

## Проблема

Интуиция врёт систематически. Не «иногда» и не «у новичков» — у всех.
То, что кажется очевидным в момент проектирования, регулярно оказывается
узким местом через год.

Поэтому решения принимаются по критериям, а не по ощущениям. Ощущения —
отправная точка для гипотезы, не источник истины.

---

## Критерии оценки

Каждое техническое решение оценивается по семи критериям.

### 1. Производительность

Измеримая дельта в горячем пути. Только измерение, не оценка.

### 2. Предсказуемость

p99 latency важнее среднего. Код с p99=50 ms неприемлем, даже если
средний = 12 ms.

### 3. Память

Пиковое потребление, фрагментация, аллокации в hot path.

### 4. Сложность

Цикломатическая сложность, когнитивная нагрузка, количество мест для
багов.

### 5. Поддерживаемость

Стоимость изменения через полгода. Стоимость онбординга нового
разработчика.

### 6. Переносимость

Работает на целевом железе без специальных обходных путей.

### 7. Соответствие стеку

Не изобретает велосипед. Использует существующие подсистемы.

## Процесс принятия решений

### Шаг 1: проблема сформулирована

«X слишком медленный» — не проблема. «X занимает 8 ms на кадр при сцене
с 100 000 вокселей, из них 6 ms — cache miss-ы в Y-структуре» — проблема.

Без измерения нет проблемы. Без проблемы нет решения.

### Шаг 2: альтернативы перечислены

Не «какое решение выбрать», а «какие варианты существуют». Минимум два.

### Шаг 3: критерии применены

Каждый вариант оценивается по семи критериям.

### Шаг 4: прототип измерен

Если ни один вариант не исключён по критериям — оба реализуются в
эксперименте и сравниваются бенчмарком.

### Шаг 5: решение задокументировано

В `agent/knowledge.md` или аналогичном документе — действующий engineering
contract с датой, контекстом, ссылкой на измерение.

---

## Документирование выбора

Формат записи в engineering docs:

```markdown
## §N. [краткое название решения]

**Дата:** YYYY-MM-DD
**Контекст:** [что решалось]
**Альтернативы:** [что рассматривалось]
**Решение:** [что выбрано]
**Критерий:** [какие критерии были приоритетны]
**Измерение:** [ссылка на benchmark output или профиль]
**Последствия:** [что это решение запрещает или требует]
```

Без записи решение не действует. Без измерения запись не принимается.

## Пример: выбор контейнера для чанков вокселей

### Проблема

Чанки вокселей — 4096 вокселей каждый. Сцена содержит 10 000 чанков.
Нужен контейнер для быстрого lookup по координатам `(x, y, z)`.

### Альтернативы

| Вариант | Производительность | Память | Сложность |
|:--------|:-------------------|:-------|:----------|
| `std::unordered_map<SparseKey, Chunk*>` | Зависит от hash | Overhead на node | Низкая |
| `flat_hash_map` (Abseil-style) | Cache-friendly | Низкий overhead | Средняя |
| `std::map<SparseKey, Chunk>` | O(log N), cache-unfriendly | Overhead на tree | Низкая |
| Sparse64Tree + flat array | O(1) cache-friendly | Минимальный | Высокая |

### Решение

Sparse64Tree + flat array. Ключ — 64-bit (x:21, y:21, z:21, type:1).
Lookup O(1) без hash, без pointer chasing, с cache-friendly итерацией.

### Обоснование

Критерий 1 (производительность) и 3 (память) приоритетны для hot path.
Критерий 4 (сложность) принимается как стоимость: больше кода в обмен
на устранение bottleneck-а.

### Измерение

Бенчмарк показывает: 3.2× быстрее `flat_hash_map` на lookup, 5.8× быстрее
`std::unordered_map`.

## Правило 80/20 для оптимизации

80% выигрыша в производительности приходит от 20% кода. Это правило
работает в обе стороны:

- 80% проблем с производительностью сидят в 20% функций.
- 80% времени оптимизации уходит на 20% усилий, которые дают видимый
  результат.

Не оптимизируй то, что не показано профилировщиком как горячее.
