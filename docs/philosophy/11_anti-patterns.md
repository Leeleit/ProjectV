# Анти-паттерны

Документ описывает запрещённые или не рекомендуемые решения в hot path
real-time движков. Здесь железо диктует правила.

---

## Анти-паттерны C++

### 1. STL в hot path

Стандартная библиотека универсальна, но не оптимальна для критических
путей.

- **`std::vector`:** в Debug медленный из-за проверок итераторов. В
  Release аллокатор общего назначения может быть медленным.
- **`std::shared_ptr`:** атомарный счётчик ссылок убивает
  масштабируемость на многопоточке. Используй `unique_ptr` или сырые
  указатели там, где владение очевидно.
- **`std::map` / `std::unordered_map`:** node-based контейнеры — убийцы
  кэша. Используй `flat_map` или open addressing hash maps. В C++26 —
  `std::hashing` с открытой адресацией.

STL спроектирована для общего случая. В GameDev требования другие:
предсказуемая latency, отсутствие аллокаций в hot path, cache locality.
Node-based контейнеры разбрасывают данные по памяти.

### 2. Исключения (`try`/`throw`/`catch`)

Не используются в Runtime.

- Оверхед на размер бинарника (RTTI, unwind tables).
- Непредсказуемое время исполнения — нарушение real-time.
- Альтернатива: коды ошибок, `std::expected<T, E>` (C++23), Contracts
  (C++26).

Исключения в C++ — zero-cost только если не бросаются. Механика
throw/catch тяжёлая.

### 3. RTTI (`dynamic_cast`, `typeid`)

Если нужно узнать тип объекта в рантайме — архитектура сломана.

- `dynamic_cast` медленный.
- Альтернатива: ECS (компоненты определяют поведение), tag dispatching,
  `enum TypeID`.

## Анти-паттерны производительности

### 4. Pointer chasing

`Object → Component → Data → Value`

Каждая стрелочка — потенциальный cache miss (100-300 тактов CPU).
Решение: Data-Oriented Design. Данные лежат в плоских массивах.

### 5. False sharing

Размещение атомиков или часто изменяемых данных разных потоков в одной
кэш-линии. Когда один поток пишет, вся линия invalidate-ится у других
ядер через MESI/MESIF/MOESI — неявный mutex.

Решение: `alignas(std::hardware_destructive_interference_size)` для
структур, используемых в разных потоках. Константа определена в `<new>`
(C++17) и автоматически выбирается под платформу: 64 на x86, 128 на
Apple Silicon.

### 6. Branch misprediction в hot path

Современный CPU «угадывает», какая ветка `if` сработает. Угадал —
конвейер летит, ошибся — сброс (10-20 тактов штрафа). В hot path
минимизируем через branchless код и сортировку данных.

Подробности: [10_manifesto.md](10_manifesto.md),
[05_hardware-tour.md](05_hardware-tour.md).

## Анти-паттерны архитектуры

### 7. Алмазное наследование

Виртуальное наследование для разрешения алмазной иерархии добавляет
косвенность, два `vtable` pointer'а, путаницу с `this`. ECS устраняет
эту проблему через композицию.

### 8. Базовый класс для всего

`class GameObject` с десятком виртуальных методов. Любой вызов идёт
через `vtable` — потенциальный cache miss + невозможность vectorization.
ECS с композицией решает эту проблему.

### 9. Виртуальные методы в hot path

Каждый вызов `virtual` — косвенность. В цикле по 1 000 000 объектов это
1 000 000 лишних обращений к `vtable`. Если метод действительно
полиморфный по типам — вынеси полиморфизм в ECS-систему. Если нет —
удали `virtual`.

### 10. Singletons с глобальным состоянием

`MyEngine::Instance().GetFoo()` — тестирование невозможно,
потокобезопасность не гарантирована, порядок инициализации не определён.
Передавай зависимости явно через конструктор.

## Когда анти-паттерн — не анти-паттерн

Контекст решает.

- `std::string` в UI, в конфигурации, в editor tools — нормально.
- Исключения в startup-коде, который выполняется один раз — нормально.
- RTTI для plugin-системы, где типы приходят из внешних библиотек —
  нормально.

Анти-паттерны — запрет для hot path. Не запрет для всего.

---

## Пример: применение в движке

В реальных движках (включая ProjectV) правила соблюдаются в `src/`. Например,
`std::unordered_map` в hot path заменён на flat hash map через кастомные
аллокаторы; `std::shared_ptr` заменён на `unique_ptr` или сырые указатели;
виртуальные методы заменены на ECS-системы с шаблонной диспетчеризацией.
