- **Name:** `ProjectV`.
- **Target:** reproducible interactive voxel MVP (ближайшая цель); долгосрочная — **песочница**, вдохновлённая
  War Thunder, Foxhole, HoI4, Warno, Supreme Commander, Minecraft и Garry's Mod.

- **Stack:** C++26, Vulkan 1.4, Data-Oriented Design (SoA по умолчанию).
- **Priority:** сохранение рабочего контекста важнее скорости.

## 5. Во время работы

### 5.1 Commit message

```
<type>(<scope>): <short imperative summary>

<1-3 строки body: что и почему, не как>
```

- **type:** `feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `build` / `chore` / `revert`.
- **scope** (опц.): `shadow` / `walk` / `voxel` / `render` / `ecs` / `platform` / `agent` / `docs` / `ci` / ...
- **summary:** ≤72 символа, imperative mood, без точки.
- **body:** 1-3 строки, wrap ~72.

**Правила:**

- **Агент НИКОГДА не коммитит автоматически.** Перед `git commit` явно спросить «Commit?». Оператор подтверждает →
  коммит.

**Запрещено:** `Co-authored-by:` и любые trailers в commit message. Аналогично `Signed-off-by:` без явного требования
оператора.

**`Refs:`** — допустимо, но **не** обязательно. Если пишете — конкретные §-номера (
`agent/knowledge.md §10.11` [Per-corner AO](#1011-per-corner-ao-landed-2026-06-10),
`agent/knowledge.md §4` [Build / verification contract](#4-build--verification-contract)) или issue/PR#. Не превращайте
commit message в список cross-refs ради ритуала.

### 5.2 Что НЕ делать как ритуал

- `git diff > /tmp/before_*.patch` (за исключением обязательного safety-net перед деструктивными операциями на грязном
  дереве).
- Поиск правильных §n для `Refs:` в non-fix коммитах.
- Автоматическое создание safety-patch в `/tmp/` после каждого рядового коммита.
- Полный sync-pass по всем документам после каждого коммита. Обновлять **только** то, что реально изменилось в рамках
  текущего scope.

### 5.3 Web search (Exa) — обязателен для сложных тем

Агент **не должен** пытаться решить сложную техническую задачу только на основе своей базовой памяти или
`agent/knowledge.md` (Part B). Использовать `web_search` (Exa / fallbacks из
`agent/knowledge.md Part B §9` [Self-audit / tool availability](#9-self-audit--tool-availability-2026-06-09)) для:

- **Свежих API-изменений библиотек** (Vulkan, Jolt, flecs, fmt, tracy, volk, VMA) — **до** погружения в `external/`
  заголовки. Особенно при обновлении (bump) сабмодулей.
- **Фич C++26** (P-номера предложений, статус поддержки в stdlib, нюансы ABI, матрица поддержки компиляторами) — **до**
  выводов о работоспособности кода в Clang/MSVC.
- **Vendor-specific behavior** (особенности GPU NVIDIA / AMD / Intel, драйверы, поведение Validation Layers и слоев
  `VK_LAYER_*`).
- **Best practices** для новых подсистем (mesh shaders, SVO, render graph, JPH API drift, ECS patterns и т.д.).
- **Внешних инструментов и CLI** (`gh` CLI, GitHub API, vulkaninfo, Tracy UI).

**Когда НЕ искать:** тривиальные задачи (переименование, стандартный рефакторинг, редактирование хорошо знакомого
локального файла). Локальный код изучается строго через `rg` / `read_file`.

**Инвариант:** возникла мысль «кажется», «должно быть» или «помню, что» по сложной теме -> сначала быстрый web search,
затем написание кода.

### 5.4 Git safety

**Требуют явного подтверждения оператора** (запрещено выполнять автоматически):

- `git commit`.
- `git rebase` (в любой форме, включая `pull --rebase`).
- `git reset --hard` для отката состояния.
- `git revert` существующих коммитов, не созданных в текущей работе.
- `git push` / `git push --force` в любые удаленные репозитории.
- Удаление веток: `git branch -D`, `git push origin --delete`.
- Публикация в сеть: `gh pr create`, `gh issue create`, создание релизов, публикация пакетов.
- Системные деструктивные команды: `sudo`, `chmod -R 777`, `dd of=...`, запись в системные каталоги за пределами проекта
  и домашней директории.
- `rm -rf` для путей, которые не были прочитаны и проверены в текущей сессии.

**Safety-net workflow** перед деструктивными действиями на грязном дереве (если есть uncommitted изменения, а требуется
деструктивная операция — инцидент `2026-06-10` с потерей P0.2 LINEAR fix):

1. Выполнить `git status -uall` для фиксации состояния.
2. Сохранить полный diff: `git diff > /tmp/before_<op>_<timestamp>.patch`.
3. Показать оператору `git diff --stat`, чтобы наглядно продемонстрировать, какие файлы изменятся или удалятся.
4. Дождаться текстового подтверждения оператора, после чего выполнить операцию.

**Безопасное сравнение с HEAD (без деструктивного удаления):** использовать `git diff HEAD -- <path>`,
`git show HEAD:<path>` или промежуточный патч `git diff HEAD -- <path> > /tmp/head_orig.patch` с последующим ручным
слиянием (merge).

### 5.5 Multi-agent coordination

Над репозиторием могут параллельно работать несколько агентов. Распределенные задачи **должны иметь строго
непересекающиеся scope** (разные файлы, модули или уровни абстракции).

**Scope discipline:**

- Запрещено коммитить файлы за пределами объявленного при старте `files-touched-intent`.
- Использовать только точечный `git add <path>`, автоматический `git add -A` строго запрещен.

**При возникновении конфликтов (merge conflict или перезапись):**

1. Прекратить автоматические попытки исправления.
2. Выполнить `git status`, `git diff` и `git log -p` для анализа обеих веток.
3. Определить автора параллельных изменений через `git log` для понимания контекста.
4. Выполнить ручной merge совместно с оператором. Автоматическое разрешение конфликтов агентом запрещено.
5. Зафиксировать резолюцию конфликта в `agent/knowledge.md Part A` (engineering contracts).

Если перед началом работы обнаружено, что предыдущая работа отсутствует в HEAD, необходимо проверить `git reflog`,
`git fsck` и патчи в `/tmp/before_*`. Запрещено строить гипотезы об удалении работы другими агентами без сверки с
логами. Обратитесь к оператору за разъяснением.

**Редактирование файлов-хабов** (`TODO.md`, `AGENTS.md`, общие шейдерные заголовки с shared-структурами, корневой
`CMakeLists.txt`):
При необходимости обновить файл-хаб выполняйте строго точечные (строчные) изменения сразу после `git pull` или ручной
проверки отсутствия свежих изменений в репозитории, чтобы избежать конфликтов слияния.

### 5.6 Shared `agent/` файлы

Файлы в директории `agent/` (кроме `AGENTS.md`, который подчиняется правилам §1) являются общей инфраструктурой. Наличие
незакоммиченных изменений от других агентов в этой папке — штатная ситуация.

**Запрещено:**

- Сбрасывать изменения в `agent/*` через `git checkout --` или `git clean`, если там присутствуют правки других агентов.
- Объявлять всю директорию `agent/*` своей исключительной зоной ответственности (scope).
- Удалять временные файлы и патчи других агентов из `/tmp/`.

### 5.7 Code quality и лимиты отладки

**Принцип:** «Fix, don't silence». Подавление предупреждений компилятора или анализатора (через грязные хаки в коде,
глобальные настройки IDE, отключение предупреждений в CMake или `.clangd`) запрещено. Если возникает ложноположительное
срабатывание (false-positive), его следует подавлять локально, точечно и с обязательным документированием причины в
коде.

При возникновении спорных архитектурных решений приоритет всегда отдается фундаментальным принципам проекта, описанным в
`legacy/docs/philosophy/`.

### 5.8 Subagent delegation (≤5 параллельных read-only процессов)

**Разрешено делегировать:**

- Поиск совпадений (grep/regex) по кодовой базе.
- Чтение и анализ связанных файлов (поиск определений, выявление архитектурных паттернов).
- Сбор аналитической информации из `legacy/docs/` по конкретному запросу.
- Параллельное сравнение результатов сборки из разных директорий сборки.

**Запрещено делегировать:**

- Любые модификации файлов (`write_to_file`, `replace_in_file` или запуск команд с флагом `requires_approval: true`).
- Деструктивные операции в Git.
- Операции с конфиденциальными данными и секретами (например, `.env`).
- Принятие решений, требующих внесения изменений в `agent/knowledge.md Part A` (engineering contracts) или
  `agent/knowledge.md Part B` (runtime facts).
- Крупные архитектурные задачи, требующие удержания широкого контекста проекта.

**Валидация результатов:** любой вывод, предоставленный субагентом, основной агент обязан верифицировать с помощью
точечных команд `read_file` или `rg` перед тем, как использовать в работе.

### 5.9 Pre-commit gate

Перед выполнением команды `git commit` агент обязан проверить соблюдение следующих условий:

1. Соответствие формата commit message правилам §5.1.
2. Получено явное подтверждение оператора на коммит (после демонстрации изменений).
3. Пройдены все проверки безопасности по работе с Git (§5.4) и соблюдена дисциплина scope (§5.5).

## 6. Definition of done

Задача считается выполненной, если полностью закрыты следующие критерии качества:

- [ ] **Сборка проекта** успешно проходит (green build) на целевой платформе (если вносились изменения в исходный код,
  шейдеры, CMake или конфигурацию сборки).
- [ ] **Автоматические тесты**, затрагивающие измененные компоненты, успешно выполняются и завершаются без ошибок.
- [ ] **Отсутствие ошибок Vulkan Validation Layers** (в консоли и логах) при запуске приложения.
- [ ] **Успешное прохождение pre-commit gate** (проверены правила §5.1, §5.4 и §5.5).
- [ ] **Актуальность документации:** файлы `agent/workspace.md` (снимок текущего состояния) и `TODO.md` обновлены,
  выполненные задачи отмечены.
- [ ] **Сохранение контекста:** в случае проведения деструктивных операций на грязном дереве восстановительный патч
  сохранен в `/tmp/` и операция была подтверждена оператором (согласно §5.4).

## 8. Comment management protocol (added 2026-06-19 per operator request)

**Принцип:** код должен быть максимально чистым от комментариев. Все комментарии о кодовой базе живут вне кода — в
выделенных файлах `COMMENTS.md` (анализ текущего API и логики) и `CHANGELOG.md` (история изменений). Агент читает и
дополняет их, но никогда не пишет произвольные пояснения в самом коде.

### 8.1 Что остаётся в коде (keep markers)

В исходном коде допустимы **только** следующие маркеры (без сопутствующего пояснительного текста):

- Лицензионные заголовки: `// Copyright ...`, `// SPDX-License-Identifier: MIT`, `// Licensed under ...`, `// (C) ...`
- IDE-хинты и директивы линтера: `// noinspection <ID>`, `// ReSharper disable ...` / `// ReSharper restore ...`
- Причины использования небезопасного/грязного кода: `// EVIL: <magic-number rationale>` (согласно
  `legacy/docs/standards/04_evil-hacks-philosophy.md`)
- Ограничения порядка включения: `// must come before ...`, `// transitively: ...`
- Маркеры автоматизации в CMake: `# TODO`, `# FIXME`, `# XXX`, `# WARNING`, `# HEURISTIC:`, `# shebang`

Любые иные содержательные комментарии в коде являются кандидатами на удаление (strip).

### 8.2 Куда переносить вытесненные комментарии

| Категория                                              | Файл           | Формат записи                                                           |
|:-------------------------------------------------------|:---------------|:------------------------------------------------------------------------|
| `design-rationale` (обоснование архитектурных решений) | `COMMENTS.md`  | `## <relpath>` + `### L<start>-L<end> (design-rationale)` + тело        |
| `intent` (описание логики работы кода)                 | `COMMENTS.md`  | то же                                                                   |
| `test-narrative` (сценарий и логика теста)             | `COMMENTS.md`  | то же                                                                   |
| `refactor-history` (git-археология изменений)          | `CHANGELOG.md` | список вида `- <file>:<line> — <summary>` по стандарту Keep a Changelog |

### 8.3 Когда агент ДОБАВЛЯЕТ комментарий

1. **Разобрался в неочевидном коде:** добавляет запись в `COMMENTS.md` в секцию соответствующего файла `## <relpath>`.
2. **Исправил баг / сделал рефакторинг:** фиксирует изменения в `CHANGELOG.md` (для важных вех) либо в `COMMENTS.md` (
   для локальных пояснений).
3. **Написал новый сложный код:** сразу фиксирует пояснения в `COMMENTS.md`, не оставляя комментариев в самом коде.

**Формат записи в `COMMENTS.md`:**

```markdown
### L<start>-L<end> (<category>)

<описание логики кода или обоснование принятого технического решения>
```

`<start>` и `<end>` — включительные номера строк (1-indexed) в файле на момент извлечения/создания комментария.

открыв их
