# AGENTS.md

Инструкции для любого агента, работающего с `ProjectV`.

Если есть конфликт между скоростью и сохранением рабочего контекста проекта, приоритет у контекста.

---

## 1. Роли документов и источники истины

Документы проекта разделены по ролям. Не смешивать их.

1. `TODO.md` — главный живой roadmap, приоритеты, backlog, риски и статус milestone.
2. `AGENTS.md` — обязательный протокол работы агента.
3. `agent/` — delta-контекст, который должен переживать сессии:
  - `agent/memory.md` — долговечные repo-specific факты и ограничения;
  - `agent/status.md` — короткий снимок текущего фокуса и ближайшего разрыва;
  - `agent/decisions.md` — живые инженерные договорённости;
  - `agent/session-checklist.md` — стартовый и финальный чеклист сессии.
4. Код, тесты и актуальные `docs/` — главный источник фактов о реальном состоянии проекта.
5. `legacy/docs/latest/philosophy` — источник инженерных принципов.
6. `legacy/docs/latest/TODO.md` и академические legacy-документы — только исторический контекст и источник идей.

Если `legacy` противоречит реальному коду или корневому `TODO.md`, верить нужно коду и корневому `TODO.md`.

---

## 2. Главное правило: не плодить дубли

- Не дублировать roadmap из `TODO.md` в `agent/`.
- Не дублировать обязательный протокол из `AGENTS.md` в `agent/` или `TODO.md`.
- Не пересказывать в `agent/` то, что уже очевидно из текущего кода и не требует отдельной памяти.
- Если информация должна пережить сессию, сначала определить её тип:
  - roadmap / приоритет / риск / backlog item -> `TODO.md`;
  - глобальное правило работы агента -> `AGENTS.md`;
  - долговечный факт / текущее состояние / решение -> `agent/`.

Если документ можно сделать короче без потери рабочего смысла, его нужно сделать короче.

---

## 3. Обязательный протокол каждой заметной сессии

Перед заметной работой агент обязан:

1. Прочитать `TODO.md`.
2. Прочитать `agent/memory.md`.
3. Прочитать `agent/status.md`.
4. Прочитать `agent/decisions.md`, если задача затрагивает архитектуру, рендер, память, данные, оптимизацию, workflow
   или структуру документации.
5. Проверить состояние рабочего дерева перед изменениями.
6. Явно определить: задача относится к `mainline`, `extension` или `R&D`.

Во время работы агент обязан:

1. Не держать важный контекст только в переписке.
2. Добавлять в `TODO.md` новые идеи, риски, развилки и полезные follow-up'ы, если они реально появились.
3. Обновлять `agent/` только той информацией, которую нельзя безопасно оставить только в `TODO.md` или коде.
4. При спорном инженерном выборе сверяться с `legacy/docs/latest/philosophy`.

После заметной работы агент обязан:

1. Обновить `TODO.md`.
2. Обновить `agent/status.md`.
3. Обновить `agent/memory.md`, если появился новый долговечный факт или ограничение.
4. Обновить `agent/decisions.md`, если принято решение, которое должно пережить текущую задачу.
5. Выполнить базовую проверку результата, если она применима.

Если код или проектный процесс изменились, а это не отражено в `TODO.md` и `agent/`, работа завершена не полностью.

## 4. Практическое направление проекта

Mainline `ProjectV` сейчас — это reproducible interactive voxel MVP.

Ближайший практический путь:

- довести текущий voxel vertical slice до честного интерактивного MVP;
- стабилизировать render/meshing/interaction/documentation/build loop;
- затем расширяться в save/load, tooling и следующий gameplay/debug layer.

Что не должно становиться блокером mainline слишком рано:

- `SVO`
- mesh shaders
- bindless-everything
- тяжёлая simulation R&D
- сложный editor
- multiplayer
- большой plugin/modding stack

Это отдельный backlog экспериментов, а не обязательный путь ближайшего milestone.

## 5. Рабочие принципы

- Производительность — обязательство, а не бонус.
- Сначала данные, потом алгоритм, потом код.
- Явный контроль лучше скрытой магии.
- Сначала рабочий vertical slice, потом усложнение архитектуры.
- Сначала mainline MVP, потом R&D.
- Измерения важнее догадок: Tracy, RenderDoc, validation layers, HUD и тесты важнее "кажется, так быстрее".
- Warning cleanup должен лечить причину, а не только симптом.
- В hot path избегать лишних аллокаций, строковой работы, лишних косвенных вызовов и непрозрачных абстракций.
- Fixed-step simulation и явные инварианты важнее хаотичного update loop.
- Ожидаемые ошибки обрабатываются явно; нарушения инвариантов должны падать рано и громко.

---

## 6. Definition of Done для заметной задачи

Задача считается закрытой только если это применимо:

- код собран;
- базовая проверка выполнена;
- не появилось новых необъяснённых ошибок, warning'ов или validation/runtime regressions;
- документация и проектный контекст обновлены;
- `TODO.md` обновлён;
- `agent/status.md` обновлён;
- `agent/memory.md` и/или `agent/decisions.md` обновлены при необходимости.

Если код изменился, а состояние проекта не зафиксировано в этих файлах, задача не закрыта.
