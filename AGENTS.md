# AGENTS.md

Стабильный протокол работы AI-агента в репозитории `ProjectV`. Содержит **только инварианты**;

---

## 1. Назначение и правило изменений

1. Файл стабильный, но изменяемый.
2. Правка — **только по явной команде оператора** в текущей сессии. Правка кода не даёт права править AGENTS.md.

---

## 2. Project metadata

- **Name:** `ProjectV`.
- **Target:** reproducible interactive voxel MVP.
- **Stack:** C++26, Vulkan 1.4, Data-Oriented Design (SoA по умолчанию).
- **Priority:** сохранение рабочего контекста важнее скорости.

1. **Код** (`.cpp`, `.hpp`, `.ixx`, шейдеры, тесты) — абсолютный приоритет при оценке реальности.
2. **`AGENTS.md`** — этот файл, протокол.
3. **`agent/memory.md`** — долговечные repo-specific факты, лимиты, run-time observations, stack conventions (§10-§11).

5. **`agent/decisions.md`** — зафиксированные инженерные/архитектурные договорённости.
6. **`agent/session-checklist.md`** — пошаговый чеклист инициализации, ведения и закрытия сессии.
7. **`docs/VulkanSDK-Linux-Docs-1.4.350.1/`** — вендорная документация Vulkan 1.4 (читать **до** rg/grep'а headers /
   `vulkaninfo`).
8. **`TODO.md`** — roadmap, активные приоритеты, риски, чекбоксы.

## 6. Во время работы

### 6.1 Commit message

```
<type>(<scope>): <short imperative summary>

<1-3 строки body: что и почему, не как>
```

- **type:** `feat` / `fix` / `refactor` / `perf` / `docs` / `test` / `build` / `chore` / `revert`.
- **scope** (опц.): `shadow` / `walk` / `voxel` / `render` / `ecs` / `platform` / `agent` / `docs` / `ci` / ...
- **summary:** ≤72 символа, imperative mood, без точки.
- **body:** 1-3 строки, wrap ~72.

**Правила:**

- **Агент НИКОГДА не коммитит автоматически.** Перед `git commit` явно спросить «Commit?». Оператор подтверждает →
  коммит.

**Запрещено:** `Co-authored-by:` и любые trailers в commit message. Аналогично `Signed-off-by:` без явного требования
оператора.

**`Refs:`** — допустимо, но **не** обязательно. Если пишете — конкретные §-номера (`agent/memory.md §10.11`,
`decisions.md §4`) или issue/PR#. Не превращайте commit message в список cross-refs ради ритуала.

### 6.2 Что НЕ делать как ритуал

- `git diff > /tmp/before_*.patch` (за исключением обязательного safety-net перед деструктивными операциями на грязном
  дереве, см. §6.4).
- Поиск правильных §n для `Refs:` в non-fix коммитах.
- Автоматическое создание safety-patch в `/tmp/` после каждого рядового коммита.
- `git add -A` (всегда добавлять файлы явно: `git add <path1> <path2>`).
- Полный sync-pass по всем документам после каждого коммита. Обновлять **только** то, что реально изменилось в рамках
  текущего scope.

### 6.3 Web search (Exa) — обязателен для сложных тем

Агент **не должен** пытаться решить сложную техническую задачу только на основе своей базовой памяти или
`agent/memory.md`. Использовать `web_search` (Exa / `https://search.exa.ai` / fallbacks из `agent/memory.md §9`) для:

- **Свежих API-изменений библиотек** (Vulkan, Jolt, flecs, fmt, tracy, volk, VMA) — **до** погружения в `external/`
  заголовки. Особенно при обновлении (bump) сабмодулей.
- **Фич C++26** (P-номера предложений, статус поддержки в stdlib, нюансы ABI, матрица поддержки компиляторами) — **до**
  выводов о работоспособности кода в Clang/MSVC.
- **Vendor-specific behavior** (особенности GPU NVIDIA / AMD / Intel, драйверы, поведение Validation Layers и слоев
  `VK_LAYER_*`).
- **Best practices** для новых подсистем (mesh shaders, SVO, render graph, JPH API drift, ECS patterns и т.д.).
- **Внешних инструментов и CLI** (`gh` CLI, GitHub API, vulkaninfo, Tracy UI).

**Когда НЕ искать:** тривиальные задачи (переименование, стандартный рефакторинг, редактирование хорошо знакомого
локального файла). Локальный код изучается строго через `rg` / `read_file`.

**Инвариант:** возникла мысль «кажется», «должно быть» или «помню, что» по сложной теме -> сначала быстрый web search,
затем написание кода.

### 6.4 Git safety

**Требуют явного подтверждения оператора** (запрещено выполнять автоматически):

- `git rebase` (в любой форме, включая `pull --rebase`).
- `git reset --hard` для отката состояния.
- `git revert` существующих коммитов, не созданных в текущей сессии.
- `git push` / `git push --force` в любые удаленные репозитории.
- Удаление веток: `git branch -D`, `git push origin --delete`.
- Публикация в сеть: `gh pr create`, `gh issue create`, создание релизов, публикация пакетов.
- Системные деструктивные команды: `sudo`, `chmod -R 777`, `dd of=...`, запись в системные каталоги за пределами проекта
  и домашней директории.
- `rm -rf` для путей, которые не были прочитаны и проверены в текущей сессии.

**Safety-net workflow** перед деструктивными действиями на грязном дереве (если есть uncommitted изменения, а требуется
деструктивная операция — инцидент `2026-06-10` с потерей P0.2 LINEAR fix):

1. Выполнить `git status -uall` для фиксации состояния.
2. Сохранить полный diff: `git diff > /tmp/before_<op>_<timestamp>.patch`.
3. Показать оператору `git diff --stat`, чтобы наглядно продемонстрировать, какие файлы изменятся или удалятся.
4. Дождаться текстового подтверждения оператора, после чего выполнить операцию.

**Безопасное сравнение с HEAD (без деструктивного удаления):** использовать `git diff HEAD -- <path>`,
`git show HEAD:<path>` или промежуточный патч `git diff HEAD -- <path> > /tmp/head_orig.patch` с последующим ручным
слиянием (merge).

### 6.5 Multi-agent coordination

Над репозиторием могут параллельно работать несколько агентов. Распределенные задачи **должны иметь строго
непересекающиеся scope** (разные файлы, модули или уровни абстракции).

**Scope discipline:**

- Запрещено коммитить файлы за пределами объявленного при старте `files-touched-intent`.
- Использовать только точечный `git add <path>`, автоматический `git add -A` строго запрещен.

**При возникновении конфликтов (merge conflict или перезапись):**

1. Прекратить автоматические попытки исправления.
2. Выполнить `git status`, `git diff` и `git log -p` для анализа обеих веток.
3. Определить автора параллельной сессии через `agent/active-sessions.md` для понимания контекста.
4. Выполнить ручной merge совместно с оператором. Автоматическое разрешение конфликтов агентом запрещено.
5. Зафиксировать резолюцию конфликта в `agent/decisions.md`.

Если при старте сессии обнаружено, что предыдущая работа отсутствует в HEAD, необходимо проверить `git reflog`,
`git fsck` и патчи в `/tmp/before_*`. Запрещено строить гипотезы об удалении работы другими агентами без сверки с
логами. Обратитесь к оператору за разъяснением.

**Редактирование файлов-хабов** (`TODO.md`, `AGENTS.md`, общие шейдерные заголовки с shared-структурами, корневой
`CMakeLists.txt`):
При необходимости обновить файл-хаб выполняйте строго точечные (строчные) изменения сразу после `git pull` или ручной
проверки отсутствия свежих изменений в репозитории, чтобы избежать конфликтов слияния.

### 6.6 Shared `agent/` файлы

Файлы в директории `agent/` (кроме `AGENTS.md`, который подчиняется правилам §1) являются общей инфраструктурой. Наличие
незакоммиченных изменений от других сессий в этой папке — штатная ситуация.

| Файл                         | Назначение                      | Правило редактирования                                                      |
|:-----------------------------|:--------------------------------|:----------------------------------------------------------------------------|
| `agent/active-sessions.md`   | Реестр активных/закрытых сессий | Изменение **только своей** строки/записи. Чужие записи — read-only.         |
| `agent/status.md`            | Снимок текущего состояния       | Добавление (APPEND) новой секции или обновление своей. Не затирать чужие.   |
| `agent/memory.md`            | Накопленные факты и лимиты      | Добавление (APPEND) новых пунктов. Запрещено удалять/менять старые пункты.  |
| `agent/decisions.md`         | Архитектурные соглашения        | Только APPEND. Новые соглашения могут перекрывать старые (`supersede: §N`). |
| `agent/session-checklist.md` | Чеклист старта/завершения       | Read-only; изменять строго по указанию оператора при изменении протокола.   |

**Запрещено:**

- Сбрасывать изменения в `agent/*` через `git checkout --` или `git clean`, если там присутствуют правки других сессий.
- Объявлять всю директорию `agent/*` своей исключительной зоной ответственности (scope).
- Удалять временные файлы и патчи других агентов из `/tmp/`.

### 6.7 Code quality и лимиты отладки

**Принцип:** «Fix, don't silence». Подавление предупреждений компилятора или анализатора (через грязные хаки в коде,
глобальные настройки IDE, отключение предупреждений в CMake или `.clangd`) запрещено. Если возникает ложноположительное
срабатывание (false-positive), его следует подавлять локально, точечно и с обязательным документированием причины в
коде.

При возникновении спорных архитектурных решений приоритет всегда отдается фундаментальным принципам проекта, описанным в
`legacy/docs/philosophy/`.

**Предотвращение бесконечных циклов отладки (Stuck Loop Limit):**
Если компиляция проекта или тесты падают 3–4 раза подряд с одной и той же ошибкой, и ваши попытки исправления не
приносят результата — **прекратите автоматические попытки**. Зафиксируйте текущий статус как
`BLOCKED: compile_error / test_fail` в `agent/status.md`, кратко опишите предпринятые шаги и гипотезы, после чего
передайте управление оператору.

### 6.8 Subagent delegation (≤5 параллельных read-only процессов)

**Разрешено делегировать:**

- Поиск совпадений (grep/regex) по кодовой базе.
- Чтение и анализ связанных файлов (поиск определений, выявление архитектурных паттернов).
- Сбор аналитической информации из `legacy/docs/` по конкретному запросу.
- Параллельное сравнение результатов сборки из разных директорий сборки.

**Запрещено делегировать:**

- Любые модификации файлов (`write_to_file`, `replace_in_file` или запуск команд с флагом `requires_approval: true`).
- Деструктивные операции в Git.
- Операции с конфиденциальными данными и секретами (например, `.env`).
- Принятие решений, требующих внесения изменений в `agent/decisions.md` или `agent/memory.md`.
- Крупные архитектурные задачи, требующие удержания широкого контекста проекта.

**Валидация результатов:** любой вывод, предоставленный субагентом, основной агент обязан верифицировать с помощью
точечных команд `read_file` или `rg` перед тем, как использовать в работе.

### 6.9 Pre-commit gate

Перед выполнением команды `git commit` агент обязан проверить соблюдение следующих условий:

1. Соответствие формата commit message правилам §6.1.
2. Получено явное подтверждение оператора на коммит (после демонстрации изменений).
3. Пройдены все проверки безопасности по работе с Git (§6.4) и соблюдена дисциплина scope (§6.5).

Если проверка не пройдена, коммит не выполняется, сессия остается в состоянии `open` со статусом
`notes: BLOCKED: <название_проверки>`.

## 7. Конец сессии

Сессия представляет собой выполнение одной логической задачи и может содержать несколько промежуточных коммитов. *
*Запрещено автоматически закрывать сессию после каждого коммита**, чтобы избежать накладных расходов на повторную
инициализацию рабочего контекста.

**Действия в течение сессии:**

- После промежуточных коммитов выполнять шаги фиксации прогресса согласно разделу 3 `agent/session-checklist.md`.
- При завершении основного объема работ выполнить шаги подготовки к завершению согласно разделу 4
  `agent/session-checklist.md` (включая проверку критериев DoD, актуализацию `TODO.md` и запрос оператору «Что
  дальше?»).

**Решения оператора по завершении:**

- **«Закрыть сессию»** -> Перевести сессию в `status: closed` в `agent/active-sessions.md` строго по шагам раздела 5
  `agent/session-checklist.md`.
- **«Новая задача»** -> Закрыть текущую сессию по процедуре и инициировать новую сессию (или продолжить текущую, если
  scope не меняется).

Временные патчи безопасности в `/tmp/before_*` удаляются только в том случае, если сессия закрыта успешно и
деструктивные операции на грязном дереве были полностью завершены и проверены.

**Исключительные ситуации (сессия остается в статусе open):**

- Сбой сборки/тестов или отклонение хуками коммита -> сессия блокируется (`BLOCKED: build` / `BLOCKED: tests` /
  `BLOCKED: gate`), подробности фиксируются в `notes` активной сессии.
- **Принудительное прерывание работы (Manual Abort):** перевести сессию в статус `status: aborted` с обязательным
  указанием причины в `notes`, оставив запись в блоке активных сессий для разбора оператором.

## 8. Definition of done

Задача считается выполненной, если полностью закрыты следующие критерии качества:

- [ ] **Сборка проекта** успешно проходит (green build) на целевой платформе (если вносились изменения в исходный код,
  шейдеры, CMake или конфигурацию сборки).
- [ ] **Автоматические тесты**, затрагивающие измененные компоненты, успешно выполняются и завершаются без ошибок.
- [ ] **Отсутствие ошибок Vulkan Validation Layers** (в консоли и логах) при запуске приложения.
- [ ] **Успешное прохождение pre-commit gate** (проверены правила §6.1, §6.4 и §6.5).
- [ ] **Актуальность документации:** файлы `agent/status.md` и `TODO.md` обновлены, выполненные задачи отмечены.
- [ ] **Сохранение контекста:** в случае проведения деструктивных операций на грязном дереве восстановительный патч
  сохранен в `/tmp/` и операция была подтверждена оператором (согласно §6.4).

## 9. Comment management protocol (added 2026-06-19 per operator request)

**Принцип:** код должен быть максимально чистым от комментариев. Все «комментарии о коде» живут
вне кода — в файлах `COMMENTS.md` (текущий API) и `CHANGELOG.md` (git-археология). Агент читает их,
дополняет, создаёт новые — но **не пишет их в самом коде**.

### 9.1. Что остаётся в коде (keep markers)

В самом коде допустимы **только** следующие маркеры (без сопровождающего текста):

- Лицензионные хедеры: `// Copyright ...`, `// SPDX-License-Identifier: MIT`, `// Licensed under ...`, `// (C) ...`
- IDE-хинты: `// noinspection <ID>`, `// ReSharper disable ...` / `// ReSharper restore ...`
- `// EVIL: <magic-number rationale>` (per `legacy/docs/standards/04_evil-hacks-philosophy.md`)
- Include-order: `// must come before ...`, `// transitively: ...`
- CMake-маркеры: `# TODO`, `# FIXME`, `# XXX`, `# WARNING`, `# HEURISTIC:`, `# shebang`
- Пустые комментарий-строки `//` или `#` (визуальный разделитель внутри keep-блока)

Любой **другой** комментарий (`//` в C++, `#` в CMake) — кандидат на strip.

### 9.2. Куда переносить вытесненные комментарии

| Категория | Файл | Формат |
|---|---|---|
| `design-rationale` (почему этот код такой) | `COMMENTS.md` | `## <relpath>` + `### L<start>-L<end> (design-rationale)` + тело |
| `intent` (что код делает) | `COMMENTS.md` | то же |
| `test-narrative` (сценарий теста) | `COMMENTS.md` | то же |
| `refactor-history` (git-археология) | `CHANGELOG.md` | bullet `- <file>:<line> — <summary>` per Keep a Changelog convention |

### 9.3. Когда агент ДОБАВЛЯЕТ комментарий

1. Понял неочевидный код → добавляет entry в `COMMENTS.md` под нужным `## <relpath>` блоком.
2. Исправил баг / сделал рефакторинг → добавляет bullet в `CHANGELOG.md` (если архитектурно значимо) или `COMMENTS.md` (если локально).
3. Написал новый неочевидный код → добавляет entry в `COMMENTS.md` сразу, **не** оставляя комментарий в коде.

**Формат записи в `COMMENTS.md`:**

```markdown
### L<start>-L<end> (<category>)

<free-form text explaining the code, or its rationale>
```

`<start>` и `<end>` — 1-indexed inclusive line numbers в файле на момент извлечения.

### 9.4. Когда агент ЧИТАЕТ комментарии

Прежде чем редактировать код, агент ОБЯЗАН:

1. `rg -A 20 '^## .<relpath>.$' COMMENTS.md` — прочитать существующие записи для файла.
2. `rg 'decisions.md §N' COMMENTS.md` — найти все перекрёстные ссылки на решения.
3. После редактирования — обновить устаревшие записи (см. §9.5) либо удалить их.

### 9.5. Stale-handling rule

Каждая запись в `COMMENTS.md` имеет line range `L<start>-L<end>`. После редактирования файла:

- Если код в этом диапазоне изменился — запись устарела. Агент ОБЯЗАН либо обновить запись
  (новый текст + новые line numbers), либо удалить её. Не оставлять stale-entries.
- Если код вне диапазона изменился — запись, скорее всего, всё ещё актуальна, но проверить стоит.

### 9.6. Что НЕ делать

- **Не писать** `//` или `///` комментарии в коде, объясняющие код. Все объяснения — в `COMMENTS.md`.
- **Не подавлять** `WARN_AS_ERROR` или warnings компилятора blanket-suppressions на собственном target'е
  проекта (см. §7.2.7). Если комментарий обосновывает suppress — он идёт в `COMMENTS.md`, не в код.
- **Не создавать** новые файлы в `docs/api/` — Doxygen-конфигурация и HTML удалены в Phase F сессии
  `session-2026-06-19T-comment-minimization-r0`. Документация живёт только в `COMMENTS.md` и `CHANGELOG.md`.
- **Не удалять** keep-markers (license, noinspection, EVIL, include-order) при редактировании — они
  являются частью tooling contract.

### 9.7. Tooling

`tools/scratch/inventory_comments.py` — re-inventory классифицирует все `//` и `#` блоки в `src/`,
`tests/`, `src/shaders/`, `CMakeLists.txt`, `cmake/*.cmake`. Output: `tools/scratch/comment-inventory.{json,csv}`
+ markdown summary. Используется для аудита (не для автоматического strip'а).

`tools/scratch/strip_comments_simple.py` — single-pass strip без inventory dependency. Парсит каждый файл
напрямую, удаляет все non-keep блоки, добавляет в `COMMENTS.md`. Idempotent (повторный запуск = no-op).

`tools/scratch/apply_phase_b.py` — **deprecated** (Phase B artifact). Использовал stale inventory indices
и был заменён на `strip_comments_simple.py`. Сохранён в `tools/scratch/` для исторического аудита.

`tools/scratch/convert_to_doxygen.py` — **deprecated** (Phase C/D artifact, отменены по итогам Phase F).
Сохранён для исторического аудита.
